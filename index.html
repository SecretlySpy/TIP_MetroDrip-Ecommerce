Local Setup & Testing Guide

MetroDrip

Run the project on your own machine

MetroDrip is a B2C e-commerce and inventory system for a Metro Manila streetwear brand. This guide takes you from a completely fresh computer to a working storefront in your browser, and then to the customer app running on an Android emulator or an iOS simulator. No prior Django, Docker, or React Native experience is assumed — every command is explained.

  • Python 3.14
  • MySQL 8.4
  • Redis 7
  • HTMX
  • Alpine.js
  • Docker
  • Expo SDK 51
  • React Native 0.74

Last verified 24 August 2026 on Linux, by running every command in Steps 1–10 and the JavaScript half of Steps 11–12: database and Redis healthy, 576 tests passing, both consoles answering, the mobile API returning a live catalogue, and Metro bundling the app. Building onto a device or emulator (npm run android, npm run ios, eas build) could not be executed on that machine and is marked where it appears.

What you are about to build

Steps 1–10 leave you with two things running at the same time on your computer:

  1. A MySQL database running inside a Docker container. This stores products, orders, stock, and customers.
  2. A Django web server running directly on your machine. This serves the storefront at http://127.0.0.1:8000/.

Your browser talks to Django, and Django talks to MySQL. Steps 11–12 then add a third piece — the MetroDrip phone app, which talks to that same Django process through the mobile API instead of serving HTML. Nothing in the app half changes the web half, so you can stop after Step 10 and still have a complete working storefront.

Why Docker for the database?

Installing MySQL directly on your computer is fiddly and different on every operating system. Docker gives everyone on the team the exact same database version and settings with one command, and you can delete it cleanly when you are done. You do not need to learn Docker to follow this guide — just three commands.

Roughly how long this takes

First time on a fresh machine: 30–45 minutes for the storefront (Steps 1–10), mostly waiting for downloads.
The app (Steps 11–12): around 15 minutes on top if you use Expo Go; budget an hour or more the first time you install the Android SDK or Xcode.
Every time after that: about 30 seconds — see the cheat sheet.

Step 5

Start the database

Make sure Docker Desktop is open and running first — look for the whale icon. Then start the two data containers: 

docker compose up -d db redis --wait

Reading that command:

  • up — create and start the containers
  • -d — “detached”, meaning they run in the background and give your terminal back
  • db redis — the database and the Redis cache. The web app itself runs on your machine, not in Docker
  • --wait — pause until both report that they are genuinely ready for connections

You should see both finish at Healthy:

Container metrodrip-mysql  Started
Container metrodrip-redis  Started
Container metrodrip-redis  Healthy
Container metrodrip-mysql  Healthy
Why start Redis when nothing seems to use it

Nothing does yet, and that is deliberate. Django ships with no CACHES setting outside the test suite, so this Redis sits idle on port 6379 until you either point CACHES at it or run the optional services sidecars. It is in this command because docker compose up -d with no arguments starts exactly these two — the sidecars sit behind a --profile services flag — so starting both here matches what the rest of the team runs and keeps the console rate limiter (Step 8) one setting away from being shared instead of per-process. Leaving it out changes nothing about the storefront.

The first run is the slow one

Docker has to download the MySQL image (a few hundred MB), the much smaller Redis image, and initialise the database. Give it a couple of minutes. Every start after that is nearly instant.

Step 6

Build the tables and load demo data

The database is running but completely empty. Two commands fix that: migrate creates the tables, and seed_demo fills them with sample products so there is something to look at. 

.venv/Scripts/python manage.py migrate
.venv/Scripts/python manage.py seed_demo
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_demo
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_demo
Do not panic if seed_demo prints all zeros

On a second run you will see Demo seed complete: categories=0, products=0, variants=0…. That is not an error. The seed is idempotent — it only reports how many rows it newly created. Zero means the data was already there from a previous run, which is exactly what should happen. Verify with the check in Step 9.

Which seed command is the real one

seed_demo is the only canonical catalogue seed: five curated products with real copy, the ones any demo or screenshot should be built from. Everything else in the repository that looks like a seed is a development fixture, and they are not interchangeable:

Command or scriptProducesUse it for
manage.py seed_demo5 curated productsCanonical. Demos, stakeholder review, screenshots
manage.py seed_mock_catalogbulk placeholdersCategory, filter, and pagination testing
seed_assignment.py, seed_more.py, seed_200.py, seed_collections.py~150+ placeholder products eachLocal pagination and performance work only
The padded fixtures stack, and they do not clean up after themselves

Each of those root-level scripts adds to what is already there rather than replacing it, so a long-lived development database drifts a long way from five products. Running the count in Step 9 on one such database on 24 August 2026 returned 1,003 products and 1,180 variants. That is fine for exercising pagination and harmless locally, but it is not what a demo should look like. To get back to a demo-shaped catalogue, reset the database (Step 13) and run migrate and seed_demo alone.

Good to know

The dev server auto-reloads. Edit a template or a view, save, refresh the browser, and your change is live — no restart needed. Press Ctrl+C in that terminal to stop it.

Browse by category

Browse Categories in the navigation bar opens a menu of every main category and its Men and Women subcategories, with a live product count beside each one.

Clicking a main category shows everything in that branch — its own products plus every subcategory's. Clicking Men or Women narrows to just that subcategory. Try /shop/?category=hoodies against /shop/?category=hoodies-men and compare the counts.

Two-factor authentication and login limits

Both consoles support TOTP two-factor authentication — the six-digit codes an authenticator app generates — and both rate-limit failed sign-ins. Neither is on by default, so the commands above give you a working console straight away. Read this before you enable either, because one of the two has no undo.

Enrolling a device is a one-way door for that account

Once an account has a confirmed TOTP device, its password alone stops working — permanently, with no opt-out path and no “remember this browser”. If you enrol your only administrator and then lose the authenticator app, you have locked yourself out of the console. On a throwaway local database that costs you a docker compose down -v; on anything shared it costs somebody their afternoon. Enrol a second administrator first, or keep the recovery path in mind.

Check where you stand before changing anything:

.venv/Scripts/python manage.py check_console_otp
.venv/bin/python manage.py check_console_otp
.venv/bin/python manage.py check_console_otp

It lists every staff account and whether a password alone would still get in:

  With a confirmed TOTP device: 0
  Without a device (2FA bypassable): 9
    - admin@metrodrip.test (administrator)
    - merchant@metrodrip.test (merchant)
    ...

Enroll a device at /admin/otp_totp/totpdevice/add/ before setting
CONSOLE_REQUIRE_OTP=1, or these accounts will be refused at login.

To enrol one, sign into /admin/ and open /admin/otp_totp/totpdevice/add/. Pick the account, save, scan the QR code with any authenticator app, then enter a code to confirm the device. The QR is labelled MetroDrip, so that is what staff will see in their app.

SettingDefaultWhat it controls
CONSOLE_LOGIN_MAX_ATTEMPTS_PER_USER5Failed sign-ins per account per 15-minute window. This is the limit that actually protects an account.
CONSOLE_LOGIN_MAX_ATTEMPTS_PER_IP20Failed sign-ins per address. Looser on purpose — office staff share one outbound IP.
CONSOLE_LOGIN_TRUSTED_PROXY_DEPTH00 reads the direct connection and ignores X-Forwarded-For. Behind a reverse proxy set it to 1, or per-address limiting just measures the proxy.
CONSOLE_REQUIRE_OTPoffRequires a code from every staff account, enrolled or not. Accounts with no device are refused outright.
Run check_console_otp before turning CONSOLE_REQUIRE_OTP on

The flag makes no exception for the superuser you would need in order to enrol anybody else, so enabling it on a console where nothing is enrolled locks out every account at once. check_console_otp --strict exits non-zero when anyone is still unenrolled, which is the form to put in a deploy gate.

Locally, the attempt counters are per process

They live in Django's cache, and this project configures no cache outside the test suite — so each server process counts on its own, in memory, and a restart forgets everything. That is convenient while you are testing (restart the server to clear a lockout) and misleading in production, where several worker processes each get their own allowance. Pointing CACHES at the Redis from Step 5 is what makes the numbers mean what they say.

Confirm the mobile API answers

The app in Step 11 talks to the same Django process through /api/mobile/v1/. You can prove that half works from a terminal, before installing a single mobile tool. Every request must carry an X-Client-Version header — the API rejects requests without one by contract, so that they can be correlated with released app versions: 

curl.exe -H "X-Client-Version: 1.0.0" http://127.0.0.1:8000/api/mobile/v1/catalog/products/
curl -H 'X-Client-Version: 1.0.0' http://127.0.0.1:8000/api/mobile/v1/catalog/products/
curl -H 'X-Client-Version: 1.0.0' http://127.0.0.1:8000/api/mobile/v1/catalog/products/

A healthy answer is a paginated product list:

{"count":1003,"next":"http://127.0.0.1:8000/api/mobile/v1/catalog/products/?page=2",
 "previous":null,"results":[{"id":1003,"name":"…","slug":"…",
 "category":{"name":"…","slug":"…"},"price":10000,"price_display":"₱100.00",
 "images":[],"review_avg":null,"review_count":0}, …]}
Read the two money fields — they explain the whole app design

price is 10000, an integer count of centavos, and price_display is the finished string ₱100.00. The server sends both, and the app renders the string it was given. The app never multiplies, adds, or rounds money anywhere — that rule is why a total on a phone can never disagree with the total in the database.

Leave the header off and you get a 400 instead, which is the expected refusal, not a fault:

{"error": {"code": "missing_client_version",
           "message": "Send the app version in the X-Client-Version header.",
           "correlation_id": "26e5951f58f94c038cb674e497227dbf"}}
Two more worth trying

/api/mobile/v1/shipping/zones/ returns the three delivery zones with their fees (NCR ₱99.00, Luzon ₱159.00, VisMin ₱199.00 as seeded), and /api/mobile/v1/orders/ returns 401 until you send a token — both correct answers, and both a faster check than launching an emulator.

Step 11

Set up the phone app

mobile/ holds the customer app: React Native on Expo SDK 51, eleven screens, iOS and Android from one TypeScript codebase. It talks to the Django server you already have running, through the /api/mobile/v1/ endpoints you can already curl from Step 9.

What the app deliberately does not do

It is a shopper app only — there is no mobile merchant or administrator console, by design; staff work stays on the web. And it performs no money arithmetic at all: prices, subtotals, shipping, and totals arrive from the server as integer centavos plus a finished display string, and the app renders the string. So a wrong total is always a server bug, never a rounding difference on somebody's phone.

What you can build, on the machine you have

This is the constraint that decides everything else on this page, and it is not a MetroDrip decision: Apple's build tools only run on macOS. Android is reachable from anywhere.

Your machineAndroidiOSWhat that means in practice
Windows Yes — emulator or a real phone No Xcode does not exist for Windows. Test iOS on a borrowed Mac or through a cloud build.
Linux Yes — emulator or a real phone No Same reason. Everything else in this guide works identically.
macOS Yes Yes — simulator or a real iPhone The only host that covers both targets.

This repository is not a plain Expo project, and it changes mode 1

mobile/ contains committed android/ and ios/ native folders, which means a development build is the intended client, not the Expo Go app from the stores. Two consequences worth knowing before you start:

  • The app targets SDK 51, and the Expo Go in the app stores tracks only the newest SDKs. On Android you can sideload the matching older client — mobile/EMULATOR.md pins Expo Go 2.31.2 for exactly this reason. On iOS you cannot install an old App Store build, so iOS means mode 2 or mode 3.
  • Because those native folders exist, an EAS build will not apply the orientation, scheme, userInterfaceStyle, backgroundColor, splash, ios, android, or plugins keys from app.json — the native projects win. Running npx expo-doctor reports this as its one failing check, which is expected here rather than something to fix.

About mobile/.env

It holds exactly one setting, EXPO_PUBLIC_API_URL, and no secrets — anything prefixed EXPO_PUBLIC_ is baked into the app bundle at build time and can be read out of any installed copy. The app is designed to hold no credentials of its own; the value below is only an address.

KVM must be available for a usable emulator — check with kvm-ok (from the cpu-checker package) and add yourself to the kvm group if it complains about permissions.

Use an API 35 image, not API 34

On an android-34;google_apis image the SDK 51 Expo Go client crashes on boot with Failed to create NativeModule 'UIManager'. The identical app and bundle run correctly on API 35. This was diagnosed on a real machine and written down in mobile/EMULATOR.md; the setup script installs 35 deliberately, so do not “simplify” it back.

iOS requires macOS. There is no Windows or Linux path — not a limitation of this project.

  • Xcode from the App Store, opened once so it can finish installing its components.
  • Command-line tools: xcode-select --install.
  • CocoaPods: brew install cocoapods. The iOS project uses Hermes and targets iOS 13.4 or newer.
  • A simulator: Xcode → Settings → Platforms → install an iOS runtime.

The first npm run ios runs pod install for you and takes a long time — fifteen minutes is normal, and it compiles a large amount of native code. Subsequent runs are much faster.

There is no committed Podfile.lock

mobile/ios/ ships a Podfile but no lock file, so your first pod install resolves fresh versions rather than reproducing somebody else's. If a pod fails to build, that is the first thing to suspect — and the resulting Podfile.lock is worth keeping locally so your own builds stay reproducible.

Expo Go is not an option on iOS here

The app targets SDK 51 and the App Store only carries an Expo Go for current SDKs, with no way to install an older one. On iOS, use npm run ios for a local development build, or an EAS development-profile build for a device.

A real phone is often the fastest option, and on Windows or Linux it is the only way to see the app on real hardware. It also needs no emulator, no virtualisation, and no system image.

  • Android: enable Developer options, turn on USB debugging, plug the phone in, accept the trust prompt, and confirm with adb devices. Then npm run android installs onto it.
  • iOS: plug the iPhone into the Mac, trust the computer, and select it as the run destination in Xcode. A free Apple ID can sign a development build for your own device; distributing to anybody else needs a paid team.
  • Either: the phone and your computer must be on the same Wi-Fi network, and EXPO_PUBLIC_API_URL must use your computer's LAN IP address — see the next section.
Finding your LAN IP

ipconfig — look for IPv4 Address under your active adapter. ipconfig getifaddr en0 for Wi-Fi. hostname -I, or ip addr show. It usually looks like 192.168.x.x or 10.x.x.x. It can change when you reconnect to the network, which is a common cause of the app suddenly going offline.

Point the app at your server — the one setting that matters

This is where most first attempts fail, and the reason is worth understanding once rather than guessing at three times. An emulator is a separate virtual computer. Inside it, 127.0.0.1 means the emulator itself — not your machine. So an app asking for 127.0.0.1:8080 is asking the emulator for a server the emulator does not have.

Where the app runsEXPO_PUBLIC_API_URLWhy
Android emulator http://10.0.2.2:8080/api/mobile/v1 Android maps 10.0.2.2 to the host machine's loopback. This is the shipped default.
iOS simulator http://localhost:8080/api/mobile/v1 The simulator shares the Mac's network stack, so localhost is the Mac.
Physical phone http://192.168.1.10:8080/api/mobile/v1 Your machine's LAN address — substitute your own. Same Wi-Fi network required.
Bind the server to 0.0.0.0, not 127.0.0.1

A server started as plain runserver listens on 127.0.0.1 only and will refuse every connection from an emulator or a phone, however correct the app's address is. For all mobile work start it as runserver 0.0.0.0:8080 — Step 12 does exactly that.

You do not need to edit ALLOWED_HOSTS

Development settings already accept 10.0.2.2, localhost, 127.0.0.1, and — while DEBUG is on — this machine's own LAN addresses, looked up at start-up. If your phone is rejected with a 400 Bad Request naming the host, that lookup failed on your network, and adding your address to ALLOWED_HOSTS in config/settings/dev.py fixes it.

Step 12

Run the app

Four things have to be running, and the order matters: each one needs the one before it. Open a terminal for each — they all keep running until you stop them.

Terminal 1 — the data containers

docker compose up -d db redis --wait

Already running from Step 5? Then this returns immediately and you can move on.

Terminal 2 — Django, bound so the app can reach it

Note both differences from Step 7: the address is 0.0.0.0:8080, and the payment provider is set explicitly so checkout can complete without PayMongo keys. 

$env:PAYMENT_PROVIDER="simulated"
.venv\Scripts\python.exe manage.py runserver 0.0.0.0:8080
PAYMENT_PROVIDER=simulated .venv/bin/python manage.py runserver 0.0.0.0:8080
PAYMENT_PROVIDER=simulated .venv/bin/python manage.py runserver 0.0.0.0:8080
You may not need to set it at all

Development settings already fall back to the simulated provider whenever no PayMongo key is configured, so on a stock .env the variable changes nothing. Setting it explicitly makes the command work the same way on a machine that does have sandbox keys — which is why the project's editor tasks set it too.

Terminal 3 — start the device

Target: 
& "$env:LOCALAPPDATA\Android\Sdk\emulator\emulator.exe" -avd MetroDrip_Pixel_API35
$ANDROID_HOME/emulator/emulator -avd MetroDrip_Pixel_API35
$ANDROID_HOME/emulator/emulator -avd MetroDrip_Pixel_API35

Substitute your own AVD name if you created one by hand — emulator -list-avds prints them. Wait for the Android home screen, then confirm the emulator is actually attached:

Run one emulator at a time

Expo installs onto the first device adb lists and does not ask. Two running emulators means a coin flip about which one gets the app, and they compete for CPU badly enough to freeze both. Close the others with adb -s emulator-5556 emu kill. 

open -a Simulator

Or let npm run ios boot one for you — it picks a default device and opens the Simulator itself, so this terminal is optional on iOS. To choose a specific device: 

xcrun simctl list devices available   # see what you have
npm run ios -- --device "iPhone 15"   # run on one of them

Nothing to start — plug the phone in. Confirm the machine can see it (adb devices on Android; the device list in Xcode on iOS), and make sure mobile/.env uses your LAN IP rather than 10.0.2.2 or localhost, neither of which means anything to a phone.

Prove it works: buy something

Because the server is running the simulated payment provider, a purchase completes end to end without any payment credentials. That makes this the single best check that every layer is connected:

  1. Splash screen → Continue as guest, or create an account.
  2. Home → tap a product → choose size, colour, and fit → Add to Cart.
  3. Cart → Checkout → fill the form → pick a delivery zone → Pay.
  4. You land on Order Tracking with the timeline showing Paid.
  5. Sign in and open Orders; the notification centre shows “Order confirmed”.
  6. In your browser, open /admin/ and find that same order under Orders.

That last step is the one worth doing. Seeing the order the phone created appear in the web console is proof that the app, the API, and the database are all the same system rather than three that merely look alike.

If step 3 fails with a network error, it is the address, not the app

A failure at checkout — or an offline banner anywhere — almost always means the app cannot reach Django. Check the server was started with 0.0.0.0:8080, and that EXPO_PUBLIC_API_URL matches where the app is running. Those two account for the large majority of first-run failures.

Mobile quality checks

Run these from mobile/ before pushing app changes:

npm run typecheck    # tsc --noEmit; silence means success
npm run lint         # eslint src

There is also a one-line check for the rule that matters most in this codebase — that the app never does money arithmetic: 

grep -rnE "(price|subtotal|total|fee)\s*[*+/-]" src/

The only acceptable matches are inside comments. A match in real code means a total is being computed on the phone, which is the one thing the app is not allowed to do.

A known dead end — do not spend an afternoon on it

On one Windows machine, every emulator stopped booting mid-session: the process starts, reports the hypervisor is working, and the virtual device then produces no output at all while adb shows it permanently offline. A new AVD, API 34 versus 35, a host reboot, stopping Docker and WSL, clearing lock files, -wipe-data, and every GPU mode were all ruled out by testing. It is written up in mobile/EMULATOR.md with the full list of what was eliminated and what is still worth trying. The app itself was verified rendering on an API 35 emulator during the same session, so this is a host problem, not an app problem. On a machine showing these symptoms, use a physical phone and move on.

Step 13

Stopping and cleaning up

GoalCommandEffect on your data
Stop the web serverCtrl + C in its terminalNone
Stop Metro / the app bundlerCtrl + C in its terminalNone
Close an Android emulatorClose its window, or adb -s emulator-5554 emu killKept inside the emulator
Stop the database, keep datadocker compose stopKept
Remove containers, keep datadocker compose downKept
Delete everything, start freshdocker compose down -vPermanently deleted
Read before typing docker compose down -v

The -v flag deletes the storage volume — every product, order, and account in your local database goes with it, and there is no undo. It is genuinely useful when you want a clean slate, but only use it deliberately. Afterwards, re-run Step 6 to rebuild. The app keeps its own local state — signed-in session, cart — inside the emulator or on the phone, so clearing the database can leave the app holding references to orders that no longer exist. Sign out, or wipe the emulator's data, if that confuses it.

Phone app problems have their own table

Emulators, Metro, the offline banner, and pod install are covered separately in Step 12, because almost all of them come down to one of two causes: the server is not bound to 0.0.0.0, or the app is pointed at the wrong address.
