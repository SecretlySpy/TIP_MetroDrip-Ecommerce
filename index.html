Local Setup & Testing Guide

MetroDrip

Run the project on your own machine

MetroDrip is a B2C e-commerce and inventory system for a Metro Manila streetwear brand. This guide takes you from a completely fresh computer to a working storefront in your browser, and then to the customer app running on an Android emulator or an iOS simulator. No prior Django, Docker, or React Native experience is assumed — every command is explained.

  • Django 5.2
  • Python 3.14
  • MySQL 8.4
  • Redis 7
  • HTMX
  • Alpine.js
  • Docker
  • Expo SDK 57
  • React Native 0.86.3

Guide refreshed 29 August 2026. The Linux and Android instructions are backed by the captured results beside each step, plus clean APK smoke tests on Android API 24 and API 36. Windows and macOS commands are maintained as equivalent setup paths; iOS compilation and App Store submission remain unverified because they require qualifying Apple hardware and credentials. No guide claim should be treated as proof of a store release.

What you are about to build

Steps 1–10 leave you with two things running at the same time on your computer:

  1. A MySQL database running inside a Docker container. This stores products, orders, stock, and customers.
  2. A Django web server running directly on your machine. This serves the storefront at http://127.0.0.1:8000/.

Your browser talks to Django, and Django talks to MySQL. Steps 11–12 then add a third piece — the MetroDrip phone app, which talks to the same Django application through the mobile API instead of serving HTML. The guide starts a second local Django process on port 8080 for that API while the storefront process remains on port 8000. Nothing in the app half changes the web half, so you can stop after Step 10 and still have a complete working storefront.

Why Docker for the database?

Installing MySQL directly on your computer is fiddly and different on every operating system. Docker gives everyone on the team the exact same database version and settings with one command, and you can delete it cleanly when you are done. You do not need to learn Docker to follow this guide — just three commands.

Roughly how long this takes

First time on a fresh machine: 30–45 minutes for the storefront (Steps 1–10), mostly waiting for downloads.
The app (Steps 11–12): budget an hour or more for the first native development build, especially if Android Studio or Xcode still needs to download an SDK.
Every time after that: about 30 seconds — see the cheat sheet.

Step 3

Create the Python environment

A virtual environment is a private folder of Python libraries that belongs to this project only. It stops MetroDrip's libraries from clashing with anything else on your computer. We create one called .venv, then install everything the project needs into it. 

uv venv .venv --python 3.14
uv pip install --python .venv/Scripts/python.exe -r requirements.txt
uv venv .venv --python 3.14
uv pip install --python .venv/bin/python -r requirements.txt
uv venv .venv --python 3.14

This downloads Django, the MySQL driver, and the rest. It takes a minute or two the first time.

About the long paths in this guide

We write out .venv/Scripts/python.venv/bin/python.venv/bin/python in full instead of “activating” the environment. It is more typing, but it works identically in every terminal and removes a whole category of “it works for me” problems. If you prefer, you can activate it once per terminal session:

source .venv/bin/activate

Step 5

Start the database

Make sure Docker Desktop is open and running first — look for the whale icon. Then start the two data containers: 

docker compose up -d db redis --wait

Reading that command:

  • up — create and start the containers
  • -d — “detached”, meaning they run in the background and give your terminal back
  • db redis — the database and the Redis cache. The web app itself runs on your machine, not in Docker
  • --wait — pause until both report that they are genuinely ready for connections

You should see both finish at Healthy:

Container metrodrip-mysql  Started
Container metrodrip-redis  Started
Container metrodrip-redis  Healthy
Container metrodrip-mysql  Healthy
Why start Redis when nothing seems to use it

Nothing does yet, and that is deliberate. Django ships with no CACHES setting outside the test suite, so this Redis sits idle on port 6379 until you either point CACHES at it or run the optional services sidecars. It is in this command because docker compose up -d with no arguments starts exactly these two — the sidecars sit behind a --profile services flag — so starting both here matches what the rest of the team runs and keeps the console rate limiter (Step 8) one setting away from being shared instead of per-process. Leaving it out changes nothing about the storefront.

The first run is the slow one

Docker has to download the MySQL image (a few hundred MB), the much smaller Redis image, and initialise the database. Give it a couple of minutes. Every start after that is nearly instant.

Step 6

Build the tables and load demo data

The database is running but completely empty. Two commands fix that: migrate creates the tables, and seed_demo fills them with sample products so there is something to look at. 

.venv/Scripts/python manage.py migrate
.venv/Scripts/python manage.py seed_demo
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_demo
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_demo
Do not panic if seed_demo prints all zeros

On a second run you will see Demo seed complete: categories=0, products=0, variants=0…. That is not an error. The seed is idempotent — it only reports how many rows it newly created. Zero means the data was already there from a previous run, which is exactly what should happen. Verify with the check in Step 9.

Which seed command is the real one

seed_demo is the only canonical catalogue seed: five curated products with real copy, the ones any demo or screenshot should be built from. Everything else in the repository that looks like a seed is a development fixture, and they are not interchangeable:

What the canonical seed does not include

seed_demo does not create the optional Men/Women category tree and does not attach product photography. Empty image arrays and neutral product placeholders are therefore expected on a clean demo database. Run seed_mock_catalog only when you specifically need the populated category, filter, and pagination examples below.

Command or scriptProducesUse it for
manage.py seed_demo5 curated productsCanonical. Demos, stakeholder review, screenshots
manage.py seed_mock_catalogbulk placeholdersCategory, filter, and pagination testing
seed_assignment.py, seed_more.py, seed_200.py, seed_collections.pyLegacy ad-hoc catalogues, from a few products to 200-per-branch targetsLocal compatibility and load work only; their output is not the canonical capture dataset
The padded fixtures stack, and they do not clean up after themselves

Each of those root-level scripts adds to what is already there rather than replacing it, so a long-lived development database can drift a long way from five products. That is fine for exercising pagination locally, but it is not what a canonical demo should look like. Count the current rows in Step 9. To get back to a demo-shaped catalogue, reset the database (Step 13) and run migrate and seed_demo alone.

Run the server

You should see the MetroDrip storefront with a product grid. 🎉

Good to know

The dev server auto-reloads. Edit a template or a view, save, refresh the browser, and your change is live — no restart needed. Press Ctrl+C in that terminal to stop it.

Browse by category

Browse Categories in the navigation bar opens a menu of every main category and its Men and Women subcategories, with a live product count beside each one. This populated two-level example requires the optional seed_mock_catalog command from Step 6; it is not part of the five-product canonical seed.

How the two levels differ

Clicking a main category shows everything in that branch — its own products plus every subcategory's. Clicking Men or Women narrows to just that subcategory. Try /shop/?category=hoodies against /shop/?category=hoodies-men and compare the counts.

Step 8

Create demo accounts (customer, merchant, admin)

MetroDrip has three login surfaces. Shoppers use the storefront account pages. Staff use two separate consoles: Merchant (/merchant/) for catalog, stock, and orders, and Administrator (/admin/) for accounts, roles, and shipping fees. A merchant cannot sign into the admin console and vice versa.

Responsive sign-in and an explicit console theme

Both staff sign-in pages use the same phone-friendly layout as the storefront while keeping a distinct Merchant or Administrator identity. Choose Light or Dark on the sign-in page; after sign-in, the same selector is at the bottom of the console sidebar. The choice is saved in this browser and shared with the storefront. Staff accounts are provisioned with create_console_account below—there is intentionally no public Merchant or Administrator sign-up form.

seed_demo loads products only — it does not create users. Open a second terminal in the project folder (leave the server running) and create the three local demo accounts below.

Two-factor authentication and login limits

Both consoles support TOTP two-factor authentication — the six-digit codes an authenticator app generates — and both rate-limit failed sign-ins. Rate limiting is active by default; blanket TOTP enforcement is off, so the commands above give you a working console straight away.

Do not use the stock device form as a beginner enrolment wizard

Once an account has a confirmed TOTP device, its password alone stops working while that device exists; there is no self-service bypass or “remember this browser”. The installed django-otp administrator form is a low-level device editor, not a verified enrolment flow: a newly saved device defaults to confirmed before the form has proved a code. This guide therefore does not direct beginners to enable TOTP. Keep CONSOLE_REQUIRE_OTP off unless an authorized operator has tested provisioning and recovery with a second administrator.

Check where you stand before changing anything:

.venv/Scripts/python manage.py check_console_otp
.venv/bin/python manage.py check_console_otp
.venv/bin/python manage.py check_console_otp

It lists every staff account and whether a password alone would still get in:

  Without a device (2FA bypassable): 2
    - admin@metrodrip.test (administrator)
    - merchant@metrodrip.test (merchant)

check_console_otp is a readiness report, not an enrolment command. The low-level device model is available to authorized administrators, but this repository does not yet provide a self-service scan-and-confirm workflow or recovery-code flow. Production TOTP rollout is therefore an operator task, not part of this local beginner setup.

SettingDefaultWhat it controls
CONSOLE_LOGIN_MAX_ATTEMPTS_PER_USER5Failed sign-ins per account per 15-minute window. This is the limit that actually protects an account.

Run check_console_otp before turning CONSOLE_REQUIRE_OTP on

The flag makes no exception for the superuser you would need in order to enrol anybody else, so enabling it on a console where nothing is enrolled locks out every account at once. check_console_otp --strict exits non-zero when anyone is still unenrolled, which is the form to put in a deploy gate after a safe enrolment process exists.

Locally, the attempt counters are per process

They live in Django's cache, and this project configures no cache outside the test suite — so each server process counts on its own, in memory, and a restart forgets everything. That is convenient while you are testing (restart the server to clear a lockout) and misleading in production, where several worker processes each get their own allowance. Pointing CACHES at the Redis from Step 5 is what makes the numbers mean what they say.

Confirm the mobile API answers

The app in Step 11 talks to the same Django application through /api/mobile/v1/. You can prove that half works from a terminal, before installing a single mobile tool. Every request must carry an X-Client-Version header — the API rejects requests without one by contract, so that they can be correlated with released app versions: 

curl.exe -H "X-Client-Version: 1.0.0" http://127.0.0.1:8000/api/mobile/v1/catalog/products/
curl -H 'X-Client-Version: 1.0.0' http://127.0.0.1:8000/api/mobile/v1/catalog/products/
curl -H 'X-Client-Version: 1.0.0' http://127.0.0.1:8000/api/mobile/v1/catalog/products/

A healthy answer is a paginated product object. The current count, IDs, names, and next-page URL depend on which optional fixtures you loaded, so check the response shape instead of comparing exact values:

{"count":<current integer>,"next":<URL or null>,"previous":null,
 "results":[{"id":<integer>,"name":"…","slug":"…",
 "category":{"name":"…","slug":"…"},"price":<centavos integer>,"price_display":"₱…",
 "images":[…],"review_avg":<number or null>,"review_count":<integer>}, …]}
Read the two money fields — they explain the whole app design

price is an integer count of centavos, and price_display is the finished peso string. The server sends both, and the app renders the string it was given. The app never multiplies, adds, or rounds money anywhere — that rule is why a total on a phone can never disagree with the total in the database.

Leave the header off and you get a 400 instead, which is the expected refusal, not a fault:

{"error": {"code": "missing_client_version",
           "message": "Send the app version in the X-Client-Version header.",
           "correlation_id": "26e5951f58f94c038cb674e497227dbf"}}
Two more worth trying

/api/mobile/v1/shipping/zones/ returns the three delivery zones with their fees (NCR ₱99.00, Luzon ₱159.00, VisMin ₱199.00 as seeded), and /api/mobile/v1/orders/ returns 401 until you send a token — both correct answers, and both a faster check than launching an emulator.

Try the shopping flow

  1. Optional fixture check: if you ran seed_mock_catalog, open Browse Categories, choose a subcategory such as Hoodies → Men, and confirm its displayed product count. Otherwise skip this check.
  2. From the canonical five-product storefront, click any product.
  3. Choose a size, colour, and fit, then add it to your cart.
  4. Open /cart/ and confirm the item and price are correct.
  5. Go to checkout and fill in the delivery details.
  6. Complete the simulated payment and confirm the public order-tracking page says Paid.
  7. In a second tab, open /merchant/ and match the new order number under Orders.
Guest and signed-in results are different

A guest checkout is verified by its public Paid tracking page and the matching merchant-console order. It does not later appear in a newly created customer account and it creates no in-app customer notification. To verify Notifications in Step 12, sign in before checkout and open the Notifications action on Home after payment.

Step 10

Run the automated tests

The project ships with backend application tests plus structural checks for this guide. The backend application tests run against the real MySQL database, not a simplified stand-in, because some tests deliberately check what happens when two people buy the last item at the same moment — behaviour that only a real database reproduces.

Docker must be running

The database container has to be up (Step 5) or every test will fail with a connection error.

.venv/Scripts/pytest
.venv/bin/pytest
.venv/bin/pytest

A clean run ends with a single summary line. The exact number of tests, warnings, and elapsed time changes as the project evolves; the durable success signal is that every collected test says passed and the process exits successfully:

The full quality gate

Step 11

Set up the phone app

mobile/ holds the customer app: React Native 0.86.3 and React 19.2.3 on Expo SDK 57 (expo ~57.0.18), with TypeScript ~6.0.3. Its twelve screen components target iOS and Android from one codebase. The app talks to the Django server you already have running through the /api/mobile/v1/ endpoints you can already curl from Step 9.

What the app deliberately does not do

It is a shopper app only — there is no mobile merchant or administrator console, by design; staff work stays on the web. And it performs no money arithmetic at all: prices, subtotals, shipping, and totals arrive from the server as integer centavos plus a finished display string, and the app renders the string. So a wrong total is always a server bug, never a rounding difference on somebody's phone.

What you can build, on the machine you have

This is the constraint that decides everything else on this page, and it is not a MetroDrip decision: Apple's build tools only run on macOS. Android is reachable from anywhere.

  • Android: enable Developer options, turn on USB debugging, plug the phone in, accept the trust prompt, and confirm with adb devices. Then npm run android installs onto it.
  • iOS: plug the iPhone into the Mac and trust the computer; then enable Developer Mode under Privacy & Security (the phone restarts) and select it as the run destination in Xcode. A free Apple ID can sign a development build for your own device; distributing to anybody else needs a paid team.

Finding your LAN IP

ipconfig — look for IPv4 Address under your active adapter. ipconfig getifaddr en0 for Wi-Fi. hostname -I, or ip addr show. It usually looks like 192.168.x.x or 10.x.x.x. It can change when you reconnect to the network, which is a common cause of the app suddenly going offline.

Point the app at your server — the one setting that matters

This is where most first attempts fail, and the reason is worth understanding once rather than guessing at three times. An emulator is a separate virtual computer. Inside it, 127.0.0.1 means the emulator itself — not your machine. So an app asking for 127.0.0.1:8080 is asking the emulator for a server the emulator does not have.

After copying mobile/.env.example to mobile/.env, open that file and set EXPO_PUBLIC_API_URL to the row for your target below. The copied default is correct only for the Android emulator.

Where the app runsEXPO_PUBLIC_API_URLWhy
Android emulator http://10.0.2.2:8080/api/mobile/v1 Android maps 10.0.2.2 to the host machine's loopback. This is the shipped default.
iOS simulator http://localhost:8080/api/mobile/v1 The simulator shares the Mac's network stack, so localhost is the Mac.
Physical phone http://192.168.1.10:8080/api/mobile/v1 Your machine's LAN address — substitute your own. Same Wi-Fi network required.
Bind the server to 0.0.0.0, not 127.0.0.1

A server started as plain runserver listens on 127.0.0.1 only and will refuse every connection from an emulator or a phone, however correct the app's address is. For all mobile work start it as runserver 0.0.0.0:8080 — Step 12 does exactly that.

You do not need to edit ALLOWED_HOSTS

Development settings already accept 10.0.2.2, localhost, 127.0.0.1, and — while DEBUG is on — this machine's own LAN addresses, looked up at start-up. If your phone is rejected with a 400 Bad Request naming the host, that lookup failed on your network, and adding your address to ALLOWED_HOSTS in config/settings/dev.py fixes it.

Prove it works: buy something

Because the server is running the simulated payment provider, a purchase completes end to end without any payment credentials. That makes this the single best check that every layer is connected:

  1. Onboarding screen → sign in as customer@metrodrip.test before checkout.
  2. Home → tap a product → choose size, colour, and fit → Add to Cart.
  3. Cart → Checkout → fill the form → pick a delivery zone → Pay.
  4. You land on Order Tracking with the timeline showing Paid.
  5. Return Home, open the Notifications action, and confirm the list contains “Order confirmed”.
  6. In your browser, open /merchant/ and match that same order number under Orders.

That last step is the one worth doing. Seeing the order the phone created appear in the web console is proof that the app, the API, and the database are all the same system rather than three that merely look alike.

Guest checkout has a smaller proof path

A guest can complete payment and use public Paid tracking, and a merchant can still match that order. A guest order does not become part of an account created later and cannot create an in-app customer notification, so do not use guest mode for the notification check above.

If step 3 fails with a network error, it is the address, not the app

A failure at checkout — or an offline banner anywhere — almost always means the app cannot reach Django. Check the server was started with 0.0.0.0:8080, and that EXPO_PUBLIC_API_URL matches where the app is running. Those two account for the large majority of first-run failures.

Mobile quality checks

Run these from mobile/ before pushing app changes:

npm run typecheck    # tsc --noEmit; silence means success
npm run lint         # expo lint

There is also a one-line check for the rule that matters most in this codebase — that the app never does money arithmetic: 

Get-ChildItem src -Recurse -File -Include *.ts,*.tsx | Select-String -Pattern '(price|subtotal|total|fee)\s*[*+/-]'
grep -rnE "(price|subtotal|total|fee)[[:space:]]*[*+/-]" src/
grep -rnE "(price|subtotal|total|fee)[[:space:]]*[*+/-]" src/

The only acceptable matches are inside comments. A match in real code means a total is being computed on the phone, which is the one thing the app is not allowed to do.
